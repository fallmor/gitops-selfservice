Crossplane non plus n'est pas un seul binaire

Ce qui tourne réellement dans crossplane-system sur ce cluster.
Différence clé – les Functions répondent dans le pipeline, en synchrone. Le Provider, lui, tourne sa propre boucle de contrôle, indépendamment, vers l'API cloud réelle.
Le duo

Flux + Crossplane – Un vrai partenariat

Aucun recouvrement. Complémentarité pure.
FLUX – Livraison d'apps & de config
  • Surveille les dépôts Git
  • Synchronise les manifestes vers le cluster
  • Gère les releases Helm
  • Déclenche les claims Crossplane via Git
CROSSPLANE – Provisioning d'infrastructure
  • Reçoit les claims d'infra depuis Git
  • Provisionne de vraies ressources cloud
  • Réconcilie le drift en continu
  • Expose le cloud comme une API Kubernetes
Git est le control plane. Flux le livre. Crossplane l'impose. Vous ne touchez jamais une console cloud.

C'est ça, la réconciliation. Pas seulement du provisioning – de l'enforcement continu de l'état désiré.

Face aux alternatives

Terraform et ArgoCD sont excellents – pour autre chose

Crossplane vs Terraform
  • Réconciliation continue – Terraform réconcilie une fois. Crossplane, en continu.
  • 200+ providers, une seule API – un seul kubectl pour tout.
  • upjet génère ces providers – à partir d'un provider Terraform existant, sans code Go à écrire à la main.
Flux vs ArgoCD
  • Pull-only – Flux n'a aucune API pour recevoir un déploiement. ArgoCD, si.
  • Fait pour Crossplane – apps et Claims traités de façon identique.
  • Image Automation intégrée – détecte les nouvelles images et met à jour Git tout seul. Chez ArgoCD, c'est un projet séparé (Argo Image Updater).
Terraform excelle en provisioning ponctuel, ArgoCD en confort d'UI. Cette stack gagne dès qu'il faut de la réconciliation continue et zéro friction entre GitOps et infra.

Q : Pourquoi pas Terraform ? R : Terraform s'exécute une fois (plan/apply). Crossplane réconcilie pour toujours. Il vit aussi dans Kubernetes, donc RBAC/audit logs/GitOps viennent gratuitement. Q : Et si Claude donne une mauvaise recommandation ? R : Ça dépend du chemin. Pour la Composition classique (Demo 1&2), le XRD contraint via enum ce qu'un développeur peut écrire – c'est borné avant même que la ressource existe. Pour le pipeline IA, function-claude génère la ressource complète ; le seul garde-fou aujourd'hui est le system prompt, qui limite les combinaisons (plan, flavor, nodes) valides. En prod, on ajouterait une validation de schéma après génération, ou un policy engine (Kyverno/OPA) avant d'appliquer quoi que ce soit venant du LLM. Q : C'est production-ready ? R : Le pattern est réel et utilisé en production. Le package function-claude montré ici est une démo – une vraie équipe le durcirait (validation, limites de coût, tests) avant de le déployer largement. Q : Pourquoi Crossplane et pas un Operator Kubernetes fait maison ? Il peut faire pratiquement la même chose. R : Vrai, techniquement. Les providers Crossplane SONT des Operators. La différence : qui écrit et maintient ce contrôleur. Un Operator maison, c'est du code Go par type de ressource à maintenir ; Crossplane fournit déjà l'Operator générique par ressource – l'équipe plateforme écrit une Composition en YAML, pas un contrôleur en Go. Et la séparation Claim/XRD/Composition donne le self-service et la recomposition multi-ressources en prime. Q : Quelles autres ressources Crossplane peut gérer ? R : Tout ce qui a une API : S3, VMs, DNS, certificats TLS, repos GitHub, topics Kafka, monitors Datadog... s'il y a un provider, Crossplane peut le gérer.
